1 · A slot computed from the label
{% if not leakage.label_slot %}
This featureset declares no label slot, so the leakage check does not run. That is not the same as there being no leak: it means nothing here names the answer, and an unsupervised set has no answer to leak. Declaring a label slot is what turns the check on.

The label slot is {{ leakage.label_slot }} and no version binds it yet, so there is no label feature to compute a closure from. The check runs on every publish against whatever fills that slot.

Nothing in the catalogue is computed from {{ leakage.feature }}, so the check has nothing to refuse today. It still runs on every publish, because a derivation added tomorrow would.
The label is {{ leakage.feature }}, filling {{ leakage.label_slot }}, and a slot computed from it is refused however many hops away. The closure is transitive and that is the part people disbelieve: a derivation of a derivation of the label is still the label, and none of the expressions in between need mention it — the hops column above is how far each one is. The check runs on what was asked for, before anything is resolved, so a leaking slot is refused whether or not a view happens to supply it: “you cannot train on the answer” is a better message than “no view supplies that”. The refusal names the feature and the label together, and the remedy is to derive from a value known before the outcome — or to declare the thing an output rather than a feature. {% if leakage.outcome_window_days %} The outcome window is {{ leakage.outcome_window_days }} days, which is how long after the decision the label is knowable at all. {% endif %}

A version that cannot fill the schema is refused, and the message says which slots are unfilled: it is not a version of this featureset, it is a different set or it is a model change, and the register decides which rather than leaving somebody to remember. The mirror refusal is a binding naming a slot that does not exist — adding a slot changes X, so it is published as a different featureset and the model can be expected to need a new version. The last column is a listing of the catalogue, not a verdict: the type check runs in the register, against the feature somebody chose.

No model version you can see declares an input schema, so there is nothing to compare this set against.
Law L-W10, contravariance in inputs: a featureset a warrant names must provide everything the kernel declares it reads. Adding a regressor is a model change and not a data change, and this is where the distinction is enforced rather than remembered. A no here is the schema_not_satisfied a fit warrant would refuse with, and until this page the only way to find out was to try to issue one. The label slot is deliberately left out of the comparison: a kernel does not read the answer. See the lattice for what would have to change. {% if blind_spot %}
This comparison is not looking at every slot this featureset has. {{ blind_spot|join(', ') }} {{ 'is' if blind_spot|length == 1 else 'are' }} inherited, and FeaturesetRegistry.schema builds the comparison from the featureset's own row rather than from what it resolves to — while publish fills the resolved schema, inherited slots included. A set composed from parents therefore publishes versions that fill its schema and then satisfies no kernel at all. What is shown above is what the platform enforces, reported rather than quietly corrected here; the correction belongs in core/features/sets.py.

Never composition, assembly or a warrant — a sealed set is final, not inert, and that is what sealing is for. Breaking a seal needs principal:manage and is recorded.
