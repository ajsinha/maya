# QA

Everything that tests MAYA from outside, in one place.

| | |
|---|---|
| [`QA-CASES.md`](QA-CASES.md) | the published case list — 3,374 cases, half generated from source |
| [`cases/`](cases/) | the hand-written half, by area, as the authors wrote it |
| [`regression_suite/`](regression_suite/) | the executable suite — [how to run it](regression_suite/README.md) |
| [`cheatsheet.md`](cheatsheet.md) | the walkthrough for a tester outside the organisation |
| [`QA-LOG.md`](QA-LOG.md) | what each pass found, and what was done about it |
| `results/` | raw output, regenerated by the suite |
| `qa_setup.py`, `qa-setup.sh` | build the estate the cheatsheet walks through |

## Why the case list and the suite are separate

`QA-CASES.md` is the claim: every part of the system has a case, and half of
them are generated from `openapi.lock.json` and the navbar so the coverage is
provable rather than asserted. `regression_suite/` is the execution.

Keeping them apart is deliberate. A case list written by whatever happened to
be easy to automate would cover what is easy to automate; a suite that could
edit the list it is measured against could always report full coverage.

## Where a number comes from

    python -m qa.regression_suite.summary

Coverage is reported against the published list only. The property sweep is
reported beside it and never added to it — it asks a different question over
identifiers nobody published, and folding the two together would let a run
claim a percentage of a list it is not walking.
