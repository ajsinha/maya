{% from "help/_macros.html" import step, concept, tip, warn, example, fields, screen, cards %} {% call concept('Two credentials, one principal') %}

People sign in with a password or through single sign-on and get a server-side session. Scripts use an API key. Both resolve to the same principal, carrying roles and grants, so the authorization rules are identical however a request arrives. Only hashes of credentials are stored, and MFA secrets are sealed at rest.

One setting, auth.mode, decides it:

{{ fields([ ('db', 'MAYA passwords only (the default)'), ('sso', 'OIDC for people; password login is refused'), ('hybrid', 'OIDC for people, passwords kept for break-glass and service accounts'), ]) }} {% call example('config/application.yaml — OIDC single sign-on', 'yaml') %} auth: mode: hybrid sso: protocol: oidc issuer: "${MAYA_OIDC_ISSUER:}" # e.g. https://login.example.com/realms/bank client_id: "${MAYA_OIDC_CLIENT_ID:maya}" client_secret: "${MAYA_OIDC_CLIENT_SECRET:}" # from the environment, never this file redirect_uri: "${MAYA_OIDC_REDIRECT_URI:http://127.0.0.1:8600/auth/sso/callback}" post_logout_redirect_uri: "${MAYA_OIDC_POST_LOGOUT_URI:}" # set: sign out at the IdP too groups_claim: groups jit_provision: "true" on_missing_group: deny group_role_map: maya-admins: [admin] quant-desk: [model_designer, model_developer] {% endcall %} {% call tip('Leaving a group takes effect at the next login') %}

Group-to-role mapping is re-applied at every sign-in, so removing someone from an IdP group removes the matching MAYA capability at their next session, with no manual step. First-time users are created with the mapped roles and no object grants.

Signing out, over OIDC. With post_logout_redirect_uri set and registered with the IdP, signing out of MAYA also sends you to the IdP's end-session endpoint, which ends your session there and returns you; empty, only the MAYA session ends. In the other direction the IdP can end a MAYA session server to server by POSTing a signed logout token to /api/v1/auth/sso/oidc/backchannel-logout. MAYA checks it as strictly as an ID token, and more: fresh, carrying the logout event, a subject or session id, a single-use jti and no nonce. Anything else is refused with a 400, audited as auth.sso_refused, and ends nothing.

{% call example('config/application.yaml — SAML 2.0 instead', 'yaml') %} auth: mode: hybrid sso: protocol: saml2 saml: sp_entity_id: "https://maya.example.com/saml" acs_url: "https://maya.example.com/auth/sso/saml/acs" idp_entity_id: "https://login.example.com/saml" idp_sso_url: "https://login.example.com/saml/sso" idp_cert_file: "/etc/maya/idp-signing.pem" # public: the IdP's signing certificate groups_attribute: groups # SAML attribute holding group names username_attribute: "" # empty: the NameID is the username {% endcall %}

Register MAYA at the IdP from its metadata, GET /api/v1/auth/sso/saml/metadata. The IdP must sign the assertion. MAYA checks the signature, issuer, audience, destination and recipient, and the validity window, and requires every Response to answer a request MAYA made, once: an unsolicited Response, a replayed Response and a replayed assertion are all refused and audited as auth.sso_refused. SAML needs python3-saml and xmlsec; without them saml2 is refused at startup, naming both.

Single logout, when auth.sso.saml.idp_slo_url is set: signing out of MAYA ends the MAYA session and sends you to the IdP to end yours there; the IdP's own LogoutRequest, which must be signed, ends every MAYA session of the person it names (only the named IdP session, when it names one). With sign_requests: true MAYA signs its AuthnRequests and logout messages with its own key pair (RSA-SHA256), and its metadata publishes the certificate.

{% call warn('Tested against one real identity provider') %}

OIDC and SAML sign-in, sign-out at the IdP, and single logout have been exercised end to end against Keycloak 26.4 only, besides a simulated IdP in the test suite; the security guide gives the exact client settings. Over SAML, logout reaches MAYA only through the browser (front channel): a SAML IdP's server-to-server (SOAP) logout does not. Over OIDC the back channel works, but Keycloak's "sign out all sessions" of a user was seen to send a logout token for only one of them. IdP-initiated sign-in is not supported, by design: it cannot be tied to a request MAYA made.

Outside the dev environment, MAYA refuses to start while the bootstrap admin still has its default password, unless app.allow_default_admin_password is set. Administrators can see and end sessions under {{ screen('/admin/users', 'Admin → Users & roles') }}.

{% endcall %} {% call step(3, 'Two-factor: codes or a security key') %}

Enroll under {{ screen('/account/mfa', 'Account → Two-factor authentication') }}: add the shown secret (or its otpauth:// link) to any authenticator app and confirm one code. After that, a password sign-in opens a session that can do nothing but verify a code.

{% call example('config/application.yaml', 'yaml') %} auth: mfa: enforce: "${MAYA_MFA_ENFORCE:auto}" # auto | true | false required_for_roles: [admin, model_owner] issuer_name: MAYA {% endcall %}

auto enforces the role requirement outside dev; in dev only users who enrolled are challenged. A user whose role requires MFA but who has not enrolled can do nothing but enroll. SSO sessions leave the second factor to the identity provider. An administrator can reset a user's enrollment; that is audited as auth.mfa_reset and removes security keys too.

Security keys and passkeys

On the same page, Add a key registers a hardware security key or a passkey (WebAuthn). A key can stand alone or sit beside an authenticator app; at the challenge, either answers. Each challenge is issued by MAYA, bound to your sign-in, single-use and valid for five minutes. A key whose signature counter fails to rise — what a cloned key does — is refused, ends that sign-in attempt and counts toward lockout. A session still owing its second factor can neither add a key nor replace its authenticator app, so a stolen password is never enough.

{% call example('config/application.yaml', 'yaml') %} auth: webauthn: rp_id: "${MAYA_WEBAUTHN_RP_ID:localhost}" # the site's domain, not an IP rp_name: MAYA origins: "${MAYA_WEBAUTHN_ORIGINS:http://localhost:8600}" # exactly what the browser shows {% endcall %} {% call tip('What MAYA does not claim about a key') %}

Attestation is not requested, so MAYA records the model a key reports (its AAGUID) but does not claim the key is hardware-backed.

{% endcall %} {% endcall %} {% call step(4, 'API keys for scripts') %}

Create keys under {{ screen('/account/keys', 'Account → My API keys') }}. A key looks like maya_<env>_<key id>_<secret>: the environment segment stops a UAT key being accepted in production, and the key id is what the audit log shows. The full key is shown once.

{% call example('A narrow, short-lived key', 'python') %} import maya.sdk as maya my = maya.connect(base_url="http://localhost:8600", api_key="maya_dev_…") key = my.auth.create_api_key( "nightly-pins", roles=["feature_manager"], # never more than you hold yourself namespaces=["eq"], cidrs=["10.20.0.0/16"], days=30) # at most auth.api_keys.max_days (365) print(key["api_key"]) # shown once {% endcall %} {% call example('Use it', 'bash') %} curl -s http://localhost:8600/api/v1/features -H "Authorization: Bearer $MAYA_API_KEY" {% endcall %} {% endcall %} {% call step(5, 'The sandbox for uploaded code') %}
