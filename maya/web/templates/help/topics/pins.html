{% extends "help/_topic.html" %} {% from "help/_macros.html" import step, concept, tip, warn, example, fields, screen, cards %} {% block body %} {% call concept('A version freezes how; a pin freezes what') %}

An approved version says how a number is produced. Resolving it tomorrow can still return different rows: a vendor restates, a late file lands. A pin removes that doubt. MAYA resolves the version as of a date, runs its quality contract, writes the result as content-addressed fragments, re-reads them to verify the hash, and seals the pin. From then on its reference names the same bytes forever.

Identical fragments are stored once, across pins and versions.'), ('shield-check', 'Quality gated', 'A failing quality check blocks the pin. It never warns and seals anyway.'), ]) }}

Reading a pin reference

{{ fields([ ('maya://feature/eq/prices@v3', 'version 3: resolved live every time you read it'), ('maya://feature/eq/prices#eom/2026-01-31', 'the sealed pin in the eom series at 31 January 2026'), ('maya://feature/eq/prices#eom', 'the latest sealed pin in the eom series'), ('maya://featureset/eq/panel#q1/2026-03-31', 'a feature-set pin; its members are pins too'), ]) }} {% call step(1, 'Approve the version first') %}

Only an approved (or published) version can be pinned. Pinning a draft is refused with the version's current state named. See Workflow and policies.

{% endcall %} {% call step(2, 'Request the pin') %}

From the feature's Pins tab ({{ screen('/catalog/features', 'Catalog → Features') }}), or from a script. Name the series, the as-of date, and optionally the knowledge time to resolve at; left out, it defaults to now and the pin's provenance records that it was defaulted.

{% call example('Command line', 'bash') %} python -m maya.cli feature pin eq/prices --version 3 --name eom --as-of 2026-01-31 # sealed 9f2c…e1 (2,480 rows, 18,432 new bytes) {% endcall %} {% call example('Python SDK', 'python') %} import maya.sdk as maya my = maya.connect(base_url="http://localhost:8600", api_key="maya_…") out = my.features.pin("eq/prices", version_no=3, pin_name="eom", as_of="2026-01-31", as_of_known="2026-02-01T08:00:00Z", # what was known then idempotency_key="eom-2026-01") # safe to retry if out["job"]: job = my.wait(out["job"]) print(job["result"]["content_hash"], job["result"]["bytes_new"]) else: print("requested — awaiting a pin authorizer") {% endcall %} {% call tip('Who can pin directly') %}

Someone holding the pin capability starts the job at once (state materializing). Anyone else's request waits in state requested until a pin authorizer approves it (my.features.approve_pin(pin_id)). In your scratch.<you> namespace you always pin directly.

{% endcall %} {% endcall %} {% call step(3, 'What the pin job does') %}
  1. Resolves the version as of the date and the knowledge time, recording a fill report.
  2. Runs the quality contract (not_null, range, unique_on_index, freshness_within …). Any failure marks the pin failed and stops.
  3. Cuts the rows into content-defined fragments and writes only the ones not already stored.
  4. Re-reads the fragments and verifies the content hash before sealing.
  5. Seals the pin, writes a pin.sealed audit entry and emits the event.

It is a saga: any error half-way (a failed check, an empty result, a resolver or lake error) leaves the pin failed with the reason, and its unreferenced fragments become reclaimable storage. It never leaves a half-sealed pin.

{% endcall %} {% call step(4, 'Use it') %} {% call example('Read and download a pin', 'python') %} ref = "maya://feature/eq/prices#eom/2026-01-31" preview = my.features.preview(ref) # rows, fill report, plan data = my.features.download(ref, format="parquet") # bytes plus a manifest {% endcall %} {% call example('Download from the command line', 'bash') %} python -m maya.cli feature download "maya://feature/eq/prices#eom/2026-01-31" \ --out prices-eom.parquet --format parquet {% endcall %} {% endcall %}

Pin states

{{ fields([ ('requested', 'waiting for a pin authorizer to approve the request'), ('materializing', 'the pin job is resolving, checking and writing fragments'), ('sealed', 'hashed, verified and immutable; readable by reference'), ('failed', 'the quality contract or the write failed; the same series and date can be requested again'), ('retired', 'withdrawn by an administrator, with a reason; the audit trail keeps it'), ]) }}

Why fragments

Consecutive month-end pins of a long history share almost all their rows. Fragment boundaries are content-defined, so an appended month changes only the fragments at the end; the rest are shared, and each new pin costs only its bytes_new. Fragment sizing is configured under lake.fragment in config/application.yaml (target_rows, min_rows, max_rows).

{% call warn('A pin series and date are unique') %}

Requesting eom/2026-01-31 twice is a conflict unless the earlier attempt failed. To capture a restatement, pin again under a new date or series; never expect a pin to change.

{% endcall %}

Compaction and vacuum

Every ingest and every pin appends files to a Delta table, so tables collect many small files. Once a day (or from {{ screen('/admin/storage', 'Admin → Storage') }}) MAYA compacts each table — rewriting small files into larger ones in one commit that changes the layout, not the content — and vacuums files no version needs once they are older than the retention window (lake.maintenance.vacuum_retention_hours, 168 by default). Both work on either lake backend.

{% call tip('Pins are untouched by it') %}

A pin is read by fragment value and row number, never by file name, and the ingest log is read at its latest version, so neither compaction nor vacuum can change what a pin or an as-of query returns. Integrity verification proves it after every run.

{% endcall %} {% call example('On demand', 'python') %} out = my.admin.lake_maintain() print(out["filesRemoved"], "small files compacted into", out["filesAdded"], "—", out["vacuumed"], "unreferenced files vacuumed") {% endcall %}
