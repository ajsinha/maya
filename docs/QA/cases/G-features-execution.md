## G. Features, parameters and execution — sequences and judgement

**493 judgement cases**, written by hand against `core/features/`, `core/parameters/`, `core/execution/` and the help pages that promise what they do. They are the half a generator cannot produce: **orderings, boundary values, races, and the combinations in which a control that is right on its own is wrong beside another one.**

`docs/QA/QA-CASES.md` already guarantees that nothing is *missing* — every operation once, every required field, every unknown identifier, every mapped refusal code, every screen. Nothing here duplicates that. Assume each operation below already has a happy path and each refusal code already has one provocation; what is written here is the **second** call, the one made in a particular order, at a particular value, or after something else moved underneath it.

Every case states its expectation **before it runs** — `accepted`, `refused` with a code, or `reported`. MAYA refuses a great deal on purpose and a test treating a 409 as a failure has misunderstood the product. Where the code could not be established from the source it is written `refused (code TBD)` and the case says what to look for. `EXPLORATORY` marks a case whose expectation cannot honestly be stated in advance — each one says what would make the outcome a defect.

Every case is **re-runnable**. The second run is where the state bugs live, and a case that only passes once proves nothing about a real deployment.
