## H. Validation, findings and monitoring — sequences and judgement

The generated list in `docs/QA/QA-CASES.md` guarantees that no operation, no
required field, no unknown identifier and no mapped refusal code is *missing*.
It cannot tell whether a control that is right on its own is still right in
combination, and it produces no orderings, no boundary values and no second
runs. These are the cases it cannot write.

Every expectation is stated before the case runs, as `accepted`, `refused
(code)` or `reported`. **`reported` carries most of the weight here**: this half
of the platform mostly raises findings rather than refusing, and a case whose
expectation is "a finding appears, with these words in it" is as much a control
as a 409. Where a code is not knowable from the source without running the
instance it is written `refused (code TBD)` with what to look for.

Run every case twice. The second run is where the state bugs are.
